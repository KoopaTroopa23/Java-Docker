Docker & Container Basics — Study Notes
Developers vs. Operations — The Old Problem


================
|  SECTION 1:  |
================


In traditional software delivery, developers wrote the code and a separate operations team handled deployment. To get an app running, operations had to manually gather and configure multiple files — dependencies, environment settings, server configs — and make them all work together on the target machine. This was slow, error-prone, and highly dependent on the specific environment it was deployed to. An app that worked fine on a developer's laptop could easily break on the server because the environments weren't identical.

How Docker Solved This

Docker packages an application together with everything it needs to run — code, dependencies, runtime, system libraries — into one self-contained unit. That unit behaves the same way no matter where it runs.

The process:

Developers write a Dockerfile — a plain text file with step-by-step instructions for how to build the application into a container (what base system to start from, what to copy in, how to run it).
The Dockerfile is used to build a Docker Image — a packaged, ready-to-run snapshot of the application and everything it needs.
The Image is used to run the application as a container — a live, running instance of that image.

Because the image contains everything the app needs, it runs the same way on a developer's laptop, a test server, or in production. That consistency is what closed the gap between developers and operations — and that convergence is a big part of what gave rise to DevOps: developers and operations working from the same reproducible artifact instead of two disconnected processes.

Docker Engine is the software that actually builds images and runs containers. It's available on Linux, Mac, Windows, and in the cloud — the same Dockerfile produces the same result regardless of platform.

-------------------------------
Essential Docker Commands     |
-------------------------------

Command	What it does

--- CONTAINER MANAGEMENT ---
docker ps                   # List all currently running containers
docker ps -a                # List all containers (including stopped ones)
docker run <image_name>     # Create and start a container from an image
docker stop <container_id>  # Gracefully stop a running container
docker rm <container_id>    # Remove a stopped container

--- IMAGE MANAGEMENT ---
docker images               # List all locally available images
docker history <image_name> # Show the history and layers of an image
docker rmi <image_name>     # Remove a local image

--- MULTI-CONTAINER (COMPOSE) ---
docker compose up --build   # Build images and start the project containers

--- COMMON RUN FLAGS & ARGUMENTS ---
-p <host_port>:<container_port>
    Makes your app reachable from your computer.
    Example: -p 9090:8080 lets you open the app at http://localhost:9090

-i
    Keeps the container running so it can accept input.
    (You usually use this together with -t.)

-t
    Makes the container act like a normal terminal window.

-it
    Opens an interactive terminal inside the container.
    You will see logs on your screen.
    You can type commands inside the container.

--name <container_name>
    Gives your container a custom name instead of a random one.

--mount type=bind,source=<host_path>,target=<container_path>
    Lets the container use a folder or file from your computer.
    Example: share logs, configs, or code with the container.

================================================================================
Notes:
* Replace placeholders like <image_name> or <container_id> with your actual data.
* Run 'docker --help' in your terminal for a full list of commands.

-----------------------------------------------------


Create a Dockerfile in the root of your project.

1)  Build your project
    ./gradlew clean build --refresh-dependencies

   docker run -p 9090:8080 java-docker

Visit http://localhost:9090 — this is the mapped port from Step 4, taking you to your Java/Docker app's endpoint through the port mapping you set up.
4)  To Run Docker in the background   docker run -d (name)     OR   docker run -d -p 9090:8080 java-docker

BUILDKIT  / buildx                      |
-----------------------------------------


BuildKit is Docker’s advanced build engine, and `docker buildx` enables all of its modern features:

1. **Cache mounts**
   Use `RUN --mount=type=cache` to speed up builds by caching package downloads and build artifacts.

2. **Secret mounts**
   Use `RUN --mount
   nt=type=secret,id=mykey` to securely access secrets (API keys, tokens) during the build without baking them into the image.

3. **Multi‑platform builds**
   Build images for multiple operating systems and architectures:
   docker buildx build --platform linux/amd64,linux/arm64 -t java-docker --push .

4. **Parallel build stages**
   Build multiple stages (e.g., frontend + backend) at the same time:
   docker buildx build -t java-docker .

DOCKER COMPOSE  |
-----------------

Docker Compose = run multiple containers together
(frontend, backend, database, etc.)

1) Create a compose.yaml file
    - List your services (app, redis, postgres, define networks)
    - Add ports if needed

2) Start everything:
    docker compose up
    Runs all services at once.

3) Stop everything:
    docker compose down

Notes:
- You do NOT use "docker run" for each service when using Compose.
- Compose replaces multiple "docker run" commands.
- Compose is for multi‑container setups.
- Document everything in Readme file

DOCKER ENGINE  |
----------------

HHow Docker works under the hood:

1) dockerd (Docker Daemon)
    - The main background service.
    - Handles containers, images, networks, volumes.

2) REST API
    - The interface the daemon exposes.
    - Lets tools talk to Docker Engine.

3) docker CLI
    - The commands you type: docker run, docker stop, docker build.
    - Sends requests to the REST API.
    - The daemon does the actual work.


------------------
LINUX NAMESPACE  |
------------------

PID
    Gives each container its own process list.
    Containers cannot see processes from other containers.

Network
    Gives each container its own network stack.
    Its own IP, ports, and network rules.

IPC
    Controls how containers share system messaging.
    Keeps container communication separate.

Mount
    Gives each container its own filesystem view.
    Controls what folders/files the container can see.

UTS
    Lets a container have its own hostname.
    Makes each container look like its own machine.

User
    Gives each container its own user and permission system.
    Maps container users to host users safely.

-------------------
DOCKER NETWORKING |
-------------------

Default Networks:
    bridge
        - The normal network for containers.
        - Containers get their own IP.
        - Containers can talk to each other.

    none
        - No network at all.
        - Container is completely isolated.

    host
        - Container shares the host’s network.
        - No port mapping needed.
        - Acts like it’s running directly on your machine.

Examples:
    docker run ubuntu
        Uses the default bridge network.

    docker run --network bridge web1
    docker run --network bridge web2
        Both containers can talk to each other.

------------------------
USER-DEFINED NETWORKS  |
------------------------

Why use them:
    - Containers can find each other by name.
    - Cleaner, easier networking.
    - No need to remember IP addresses.

Commands:

    docker network create mynet
        Creates a custom network.

    docker run --network mynet --name web1 <image>
    docker run --network mynet --name web2 <image>
        Containers can talk using names:
            web1 → web2
            web2 → web1

    docker inspect mynet
        Shows details about the network.

DOCKER REGISTRY   |
-------------------

A Docker Registry is a place where container images are stored.

Think of it like a big online folder for images.

Examples:
    Docker Hub
    GitHub Container Registry
    Private company registries

What happens:
    - When you PUSH an image, it goes to the registry.
    - When you RUN an image (like nginx), Docker pulls it from the registry.

Example:
    docker run nginx
        This pulls the nginx image from Docker Hub.

-------------------------
CONTAINER ORCHESTRATION |
-------------------------

Why we need orchestration:
    - More users = more load → need more containers.
    - If a host crashes, your app should keep running.
    - You want automatic scaling (up/down).
    - You want load balancing.
    - You want storage + config handled for you.
    - You want to run hundreds or thousands of containers easily.

What orchestration does:
    - Starts containers across multiple machines.
    - Restarts containers if they fail.
    - Replaces crashed hosts automatically.
    - Scales your app up or down.
    - Distributes traffic (load balancing).
    - Manages storage and configuration.

------------------------
DOCKER SWARM (SIMPLIFIED)
------------------------

Easy to set up.
Not ideal for large production apps.
Basic auto‑scaling only.

How it works:
    - Multiple hosts (machines).
    - One becomes the Swarm Manager.
    - Others become Worker Nodes.

Commands:
    docker swarm init
        Creates the swarm on the manager.

    docker service create --replicas=3 <image>
        Runs 3 copies of your app across the swarm.

Notes:
    - Swarm lets you manage all nodes from one place.
    - You don’t log into each machine manually.



--------------------
KUBERNETES          |
--------------------
How they work together:

Docker:
    - Builds your container image.
    - Packages your Java app.
    - Creates the thing you deploy.

Kubernetes:
    - Runs your containers on many machines.
    - Handles scaling, load balancing, restarts, and failures.
    - Can run thousands of container copies with one command.

Think of it like this:
    Docker = "Make my app into a container."
    Kubernetes = "Run my containers everywhere automatically."


------------------------
KUBERNETES ARCHITECTURE |
------------------------

Cluster
    A group of machines (nodes) working together.

Worker Node
    Runs your containers (called Pods).

Master (Control Plane)
    Watches all worker nodes.
    Decides where containers should run.

Main Master Components:
    api-server      → Front door for all commands.
    etcd            → Stores cluster data.
    scheduler       → Decides which node runs a pod.
    controllers     → Make sure everything stays healthy.

On each Worker Node:
    kubelet         → Talks to the master.
    CRI             → Container Runtime Interface.
    containerd/CRI-O→ Actually runs the containers.
